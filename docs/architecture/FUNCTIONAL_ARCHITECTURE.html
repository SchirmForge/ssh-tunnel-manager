1. Overview and principles

SSH Tunnel Manager is a secure SSH tunnel manager for Linux with both a graphical and a command-line interface. A long-running daemon owns every SSH connection; clients drive it over a local REST API and receive live updates over a Server-Sent Events stream. The daemon can also run on a different machine, reached over HTTPS, while SSH private keys stay on that machine.

PrincipleWhat it means in practice
Security firstMemory-safe implementation, credentials behind the Secret Service/keyutils facade, least privilege, authentication on by default, HTTPS required for any non-loopback access, and structured protocol data as the only UI control plane.
Unix philosophyThe daemon does one thing. Everything else talks to it through a documented API.
User choiceGUI for interactive use, CLI for scripting and servers. Both are first-class and share the same client logic.
Remote capabilityA client can manage a daemon on another host without the private keys ever crossing the network.
Event-drivenThe daemon never blocks on a human. When it needs a credential it emits an event and waits for an answer over the API.

3.2 Shared library — crates/common

✅ Implemented — the spine every client and the daemon build on.

  • Profile types with validation and TOML persistence, including backward-compatible reading of the pre-v0.1.7 boolean password_storage field
  • EventListener: the single SSE client, shared by CLI and GUI, reconnecting with exponential backoff
  • Daemon client: connection modes, token header, TLS pinning, socket path discovery, config validation
  • start_tunnel_with_events / stop_tunnel: the SSE-first control flow both front-ends use, with a TunnelEventHandler trait for the interactive parts
  • Credential-store facade with Secret Service/keyutils selection, migration, availability reporting and graceful fallback
  • SSH private-key inspection and local-file validation shared by clients without exposing russh to GUI crates

3.4 GUI — gui-core, gui-gtk and gui-v2

🧪 Parallel delivery: gui-gtk is packaged; gui-v2 is source/automated validated and awaits runtime acceptance and cutover.

gui-core owns immutable snapshots, typed commands/effects, action availability, feature capabilities, FIFO authentication state, profile-editor contracts, GUI preferences, pre-runtime client setup, daemon/profile effects and presentation-ready models. Toolkit adapters render a snapshot and dispatch AppCommand; they do not call daemon endpoints or mutate profile files independently. AppCore remains only for compatibility with gui-gtk.

  • gui-gtk: packaged application, including the first-launch configuration wizard
  • gui-v2: first-launch snippet/manual client setup, adaptive search/filter/sort/pin/order views, details, safe CRUD, authentication, daemon information, empty and offline states
  • Profile actions use the same toolkit-neutral command surface intended for a future tray adapter
  • Unsupported behavior is labelled WIP; useful form reveal/hide and validation still operate without false persistence or success
  • Daemon copy is display-only. Event/request/status variants, IDs, capabilities and booleans select every action and state transition
  • Help and About are Markdown assets bundled in gui-core/assets/

GUI v2 inspects cli.toml before constructing its daemon runtime. A valid file proceeds directly; a daemon-generated snippet is offered for import; and missing, unreadable, malformed or incomplete configuration stays in a setup-required state. Network snippets with an empty host request the actual connection target. Manual setup exposes mode-specific Unix socket, HTTP or HTTPS fields, validates by typed field codes, and atomically installs a 0600 file before normal health/SSE work starts. This flow configures a client connection and never starts or restarts the daemon.

4. Data flow

4.1 Who is involved in each credential

Authentication is not one interaction but several, and they do not involve the same participants. The distinction matters, because it is what determines whether a profile can ever connect without a human present.

CredentialChallenged byAnswered byDoes the SSH server see it?
Host key fingerprint The daemon, on seeing an unknown host User, via the client No. The server presents its key; the decision is local and is recorded in known_hosts
Key passphrase The daemon, on finding the key encrypted User, via the client No. It decrypts the private key inside the daemon. Only the resulting signature reaches the server
Password The daemon, or the server via remaining_methods User, the daemon's credential store, or a client-held credential response Yes. Sent to the server for validation
Two-factor code The server, as a keyboard-interactive challenge User, via the client Yes. The server issues the prompt text and validates the answer

The first two never reach the server, so a daemon-held credential store can satisfy them with nobody watching. The fourth cannot be satisfied that way at all: a TOTP code is single-use and issued by the server at the moment of connection. That is why a PasswordWith2FA profile can never reconnect unattended — see §4.3.

4.2 Interactive connection establishment

The fullest case: an unknown host, an encrypted key, and a server that wants a second factor. Each phase is conditional — a known host, an unencrypted key or a server content with the key alone simply skips the corresponding band.

Why this shape. Because every prompt travels as an event rather than a blocking call, the same daemon serves an interactive GUI, a terminal session and a headless script without knowing which is attached — and it can run as a system service with no controlling terminal. The client is a relay too: it renders whatever the daemon asks for and posts the answer back, so adding a front-end needs no daemon change.

4.3 Unattended connection

When the profile's authentication needs no human, the exchange collapses to the daemon and the SSH server, with a daemon-held credential store supplying whatever secret is required. No client need be attached at all — any that is simply observes the resulting events.

A profile takes this path when all of the following hold:

  • the host key is already in known_hosts
  • authentication is by key with no passphrase, or the passphrase/password is available in a daemon-held credential store
  • the server does not demand a second factor

❌ Auto-reconnect is not implemented. This flow describes what happens today on a normal start; nothing yet re-runs it after a drop. crates/daemon/src/monitor.rs is an empty stub and run_tunnel() connects exactly once, so auto_reconnect, reconnect_attempts and reconnect_delay are read and displayed but never acted on.

When it is built, this diagram is the only path it can use. A profile that needs any arrow reaching the user in §4.2 cannot reconnect without one, which is the reasoning behind the eligibility table in ROADMAP.md.

4.4 Event stream

Both flows above carry their events over the same channel. A client subscribes to /api/events and keeps the connection open. The daemon pushes lifecycle events and a periodic heartbeat; the shared EventListener reconnects with exponential backoff, and the GUI treats a missed heartbeat as loss of the daemon. 

{"type": "starting",      "id": "..."}
{"type": "connected",     "id": "..."}
{"type": "disconnected",  "id": "...", "reason": "..."}
{"type": "error",         "id": "...", "error": "..."}
{"type": "auth_required", "id": "...", "request": { ... }}
{"type": "heartbeat",     "timestamp": "..."}

auth_required is the only one that expects an answer, and it is answered out of band with POST /api/tunnels/{id}/auth — SSE is one-directional. The request carries an id that the answer must echo, so a late reply to a superseded prompt is rejected rather than misapplied.

Profile metadata is flattened at the top level rather than nested under a section. password_storage also accepts the pre-v0.1.7 boolean form, so profiles written by older versions still load. The legacy keychain value is resolved from the structured client/daemon connection location and is no longer written by GUI v2.

ui.toml stores only profile order, pinned IDs, connected-only filtering and sort mode. Missing or malformed preferences fall back safely, stale IDs are discarded and new profiles are appended deterministically. Deleting it cannot alter a connection profile.

Protocol-control invariant. Prompt, message, instruction, name, error and descriptive status strings received from the daemon may be displayed or logged, but are never searched or parsed to select a control or action. Future host, key and fingerprint facts must be added as structured protocol fields rather than extracted from text.

6. API behaviour

The default base is the Unix socket at $XDG_RUNTIME_DIR/ssh-tunnel-manager/ssh-tunnel-manager.sock. TCP modes exist for local testing (HTTP, loopback only) and remote access (HTTPS).

EndpointBehaviour
GET /api/healthLiveness check
GET /api/daemon/infoVersion, uptime, listener mode, SSH key directory, active tunnel count
POST /api/daemon/shutdownGraceful shutdown
GET /api/tunnelsActive tunnels and their statuses
POST /api/tunnels/{id}/startStart a tunnel; body carries the profile source mode, and the profile itself in Hybrid mode
POST /api/tunnels/{id}/stopStop a tunnel, whether connected or mid-authentication
GET /api/tunnels/{id}/statusStatus plus any pending authentication request
GET /api/tunnels/{id}/authFetch the pending authentication request
POST /api/tunnels/{id}/authAnswer it — the request id must match, so a stale answer cannot be replayed
GET /api/eventsSSE stream of lifecycle events and heartbeats

Access policy

  • Authentication is on by default in every mode; the token is generated at first start and stored 0600.
  • Plain HTTP is restricted to loopback. Binding tcp-http to a network address is refused at startup.
  • Remote access requires HTTPS, with optional certificate fingerprint pinning. Without a pinned fingerprint the client validates against public roots, so a self-signed daemon certificate is correctly refused — pinning is what makes it usable.

Profile CRUD over the API is not implemented; profiles are managed on the client side.
