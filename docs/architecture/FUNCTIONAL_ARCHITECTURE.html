1. Overview and principles

SSH Tunnel Manager is a secure SSH tunnel manager for Linux with both a graphical and a command-line interface. A long-running daemon owns every SSH connection; clients drive it over a local REST API and receive live updates over a Server-Sent Events stream. The daemon can also run on a different machine, reached over HTTPS, while SSH private keys stay on that machine.

PrincipleWhat it means in practice
Security firstMemory-safe implementation, credentials in the OS keyring, least privilege, authentication on by default, HTTPS required for any non-loopback access.
Unix philosophyThe daemon does one thing. Everything else talks to it through a documented API.
User choiceGUI for interactive use, CLI for scripting and servers. Both are first-class and share the same client logic.
Remote capabilityA client can manage a daemon on another host without the private keys ever crossing the network.
Event-drivenThe daemon never blocks on a human. When it needs a credential it emits an event and waits for an answer over the API.

3.2 Shared library — crates/common

✅ Implemented — the spine every client and the daemon build on.

  • Profile types with validation and TOML persistence, including backward-compatible reading of the pre-v0.1.7 boolean password_storage field
  • EventListener: the single SSE client, shared by CLI and GUI, reconnecting with exponential backoff
  • Daemon client: connection modes, token header, TLS pinning, socket path discovery, config validation
  • start_tunnel_with_events / stop_tunnel: the SSE-first control flow both front-ends use, with a TunnelEventHandler trait for the interactive parts
  • Keychain access with availability detection and graceful headless fallback

3.3 CLI — ssh-tunnel

✅ Implemented — for scripting, servers and power users.

AreaCommandsStatus
Profilesadd, list, info, delete✅
Tunnelsstart, stop (--all), restart, status (--all)✅
Eventswatch✅
Daemon controldaemon start, daemon stop, daemon status❌ stubs

add is interactive by default and fully scriptable with --non-interactive. Output is a formatted table or JSON. Profile editing is done in the GUI or by editing the TOML file; there is no edit command.

3.4 GUI — crates/gui-core + crates/gui-gtk

✅ Implemented (GTK4 / libadwaita).

gui-core holds everything that is not toolkit-specific — profile operations, view models with formatted display data and status colours, the AppCore application state, and the event-handling trait. gui-gtk supplies the widgets. Roughly 60–70% of the GUI is reusable by a second toolkit.

  • First-launch configuration wizard with automatic snippet detection
  • Full profile CRUD in a GNOME-Settings-style dialog, with an advanced options section
  • Live status dots driven by the SSE stream, and daemon connection monitoring with heartbeat timeout
  • Authentication dialogs whose state is driven by SSE rather than local guesses
  • Help and About rendered from Markdown bundled in gui-core/assets/

3.5 Qt GUI — crates/gui-qt

❌ Does not currently compile — the cxx-qt 0.8.0 bridge macro fails to parse.

It remains a workspace member so it can be built explicitly with cargo build -p ssh-tunnel-gui-qt, but it is excluded from default-members so it cannot break the default build or CI. Use the GTK GUI.

4. Data flow

4.1 Connection establishment

Why this shape. Because the prompt travels as an event rather than a blocking call, the same daemon serves an interactive GUI, a terminal session and a headless script without knowing which is attached — and it can run as a system service with no controlling terminal.

4.2 Event stream

A client subscribes to /api/events and keeps the connection open. The daemon pushes lifecycle events and a periodic heartbeat; the shared EventListener reconnects with exponential backoff, and the GUI treats a missed heartbeat as loss of the daemon. 

{"type": "starting",      "id": "..."}
{"type": "connected",     "id": "..."}
{"type": "disconnected",  "id": "...", "reason": "..."}
{"type": "error",         "id": "...", "error": "..."}
{"type": "auth_required", "id": "...", "request": { ... }}
{"type": "heartbeat",     "timestamp": "..."}

4.3 Health monitoring and reconnection

❌ Not implemented. crates/daemon/src/monitor.rs is an empty stub and run_tunnel() connects exactly once. The auto_reconnect, reconnect_attempts and reconnect_delay profile options are read and shown in both front-ends, but nothing acts on them. The agreed design — a global setting with a per-profile override, attempted only where authentication needs no human — is recorded in ROADMAP.md.

Profile metadata is flattened at the top level rather than nested under a section. password_storage also accepts the pre-v0.1.7 boolean form, so profiles written by older versions still load.

6. API behaviour

The default base is the Unix socket at $XDG_RUNTIME_DIR/ssh-tunnel-manager/ssh-tunnel-manager.sock. TCP modes exist for local testing (HTTP, loopback only) and remote access (HTTPS).

EndpointBehaviour
GET /api/healthLiveness check
GET /api/daemon/infoVersion, uptime, listener mode, SSH key directory, active tunnel count
POST /api/daemon/shutdownGraceful shutdown
GET /api/tunnelsActive tunnels and their statuses
POST /api/tunnels/{id}/startStart a tunnel; body carries the profile source mode, and the profile itself in Hybrid mode
POST /api/tunnels/{id}/stopStop a tunnel, whether connected or mid-authentication
GET /api/tunnels/{id}/statusStatus plus any pending authentication request
GET /api/tunnels/{id}/authFetch the pending authentication request
POST /api/tunnels/{id}/authAnswer it — the request id must match, so a stale answer cannot be replayed
GET /api/eventsSSE stream of lifecycle events and heartbeats

Access policy

  • Authentication is on by default in every mode; the token is generated at first start and stored 0600.
  • Plain HTTP is restricted to loopback. Binding tcp-http to a network address is refused at startup.
  • Remote access requires HTTPS, with optional certificate fingerprint pinning. Without a pinned fingerprint the client validates against public roots, so a self-signed daemon certificate is correctly refused — pinning is what makes it usable.

Profile CRUD over the API is not implemented; profiles are managed on the client side.
