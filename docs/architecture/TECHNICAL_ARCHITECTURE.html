1. Key design decisions

1.1 Event-driven authentication

Decision
The daemon emits an event when it needs a credential; the client prompts and answers over the API. The daemon never blocks on a human.
Rationale
Supports multi-step flows (key, then password, then keyboard-interactive) without the daemon knowing which client is attached. It can therefore run as a system service with no controlling terminal, and the CLI and GUI behave identically.
Implementation
A oneshot channel per prompt, held in the tunnel's pending_auth slot and answered through POST /api/tunnels/{id}/auth. The request carries an id that must match, so a stale answer cannot be replayed. Dropping the sender cancels the wait immediately, which is how a stop mid-authentication returns without sitting out AUTH_RESPONSE_TIMEOUT.

1.2 REST for commands, SSE for updates

Decision
A small REST API for actions, and a Server-Sent Events stream for state changes.
Rationale
REST is trivially debuggable with curl. SSE gives server push without WebSocket framing, works unchanged over a Unix socket, HTTP and HTTPS, and is browser-compatible should a web UI ever appear.
Alternatives considered
gRPC — disproportionate here, and harder to inspect. WebSocket — bidirectional framing that nothing needs, since commands already have a natural request/response shape. D-Bus — Linux-only and awkward from async Rust.
Consequence
SSE is one-directional, so an auth answer travels as a separate POST rather than back up the stream. That split is why the request-id check in 1.1 exists.

1.3 Hybrid profile mode for remote daemons

Decision
When the daemon is remote, the client sends the profile with the start request, but the SSH private key stays on the daemon host and is referenced by filename.
Rationale
The private key never crosses the network, in either direction, so there is no key synchronisation, no encrypted transfer format, and no new place for a key to leak. The user copies keys to the daemon host once, deliberately.
Implementation
ProfileSourceMode::{Local, Hybrid, Remote}. prepare_profile_for_remote() reduces the key path to its filename before transmission; the daemon resolves it against its own SSH directory and reports that directory through DaemonInfo.ssh_key_dir so error messages can name the real path.

1.4 One Tokio task per tunnel

Decision
A single async runtime, with one tokio::spawn per active tunnel.
Rationale
Tokio multiplexes tasks over a work-stealing pool, so a tunnel costs a task rather than a thread. Each task owns its state and its own shutdown channel, so tunnels fail and stop independently.
Alternative considered
A thread per tunnel — needless overhead, and harder to cancel cleanly.
Consequence
Shared state lives behind Arc<RwLock<HashMap<Uuid, ActiveTunnel>>>, which makes lock discipline load-bearing. See §3.

1.5 Runtime-selected credential store

Decision
Use Secret Service on a desktop, fall back to kernel keyutils on a headless Linux host, and keep the selected location explicit.
Rationale
Encryption at rest is the OS's job, not ours. The same binaries must also work without a desktop session. Store selection must be visible because an unexpected backend looks exactly like an empty store, and keyutils credentials do not survive reboot.
Implementation
keyring-core plus the Secret Service and keyutils store implementations. credential_store selects auto, secret-service, keyutils or none. PasswordStorage distinguishes client and daemon-host; legacy keychain is read and resolved but no longer written by GUI v2.

1.6 Toolkit-neutral GUI controller and effect runtime

Decision
GTK views render immutable AppSnapshot values and dispatch typed AppCommand values. gui-core owns the reducer, effects, preferences, editor rules, authentication queue and profile-action availability.
Rationale
Daemon/profile/security behavior is testable without GTK and cannot drift between the main window and a future tray. Widgets stay presentation-only, while ActionAvailability is the single source for enabled operations.
Consequence
gui-v2 bridges the GLib main context to a dedicated Tokio runtime thread through messages. GTK objects never cross to Tokio tasks. The outgoing AppCore remains only for gui-gtk compatibility.

1.7 Structured protocol data is the UI control plane

Decision
Daemon prompt, message, instruction, name, error and descriptive status strings are presentation-only. Request/event/status variants, IDs, capabilities and explicit booleans select every dialog, action and state transition.
Rationale
Text may be localized, misleading, changed by the server or absent. Parsing it is brittle and can turn display copy into a security boundary.
Consequence
Unknown or contradictory codes fail closed. Future host/key/fingerprint fields must be added to the daemon protocol; string parsing is not a fallback or future backlog item.

1.8 At-least-once prompt delivery, reconciled by the daemon

Decision
On subscribe, the daemon replays an auth_required for every tunnel with an outstanding prompt. Re-delivery keeps the same request id; clients dedupe.
Rationale
/api/events is a live broadcast, so a prompt raised while no client was attached — including during a reconnect — was unrecoverable and expired after AUTH_RESPONSE_TIMEOUT with nothing shown to the user. Reconciling daemon-side fixes every client at once, rather than each front-end inventing its own recovery.
Why not a fresh id per delivery
It looks like it sidesteps duplicate handling, but it breaks multi-client. submit_auth_by_request_id matches the pending request's id, so reissuing it stales the id a client is already holding and its answer fails with “Request ID mismatch”. Correctness would depend on how many clients happened to be attached. The id identifies the question, not the delivery; a genuinely new question, such as the prompt after a rejected password, still gets a new id.
Consequence
Clients must tolerate seeing a prompt twice. The CLI tracks answered request ids; the GUI keys its one active modal by request id and its pending-prompt insert is idempotent.

3. Concurrency and task model

The daemon runs one #[tokio::main] runtime. Tunnel state lives in Arc<RwLock<HashMap<Uuid, ActiveTunnel>>>, and each tunnel is a spawned task holding an mpsc shutdown receiver.

Lifecycle of a tunnel task

run_tunnel()
  ├─ select! {
  │    establish_connection()   // TCP, key exchange, host key check, authentication
  │    shutdown_rx.recv()       // cancellable throughout
  │  }
  └─ monitor_tunnel()           // runs the forward until it ends or is stopped

Lock discipline is the sharp edge here. A tunnel task needs the tunnels write lock to record its own final status. Any code that holds that lock while awaiting the task will therefore deadlock until its own timeout.

TunnelManager::stop did exactly that until v0.1.11: it held the write lock across the await on the join handle, so every cancellation during connect or authentication timed out and force-aborted the task instead of stopping it cleanly. It is now two phases — classify and take the handles under the lock, then release it before signalling and waiting. Do not reintroduce an await inside that critical section.

Timeouts

ConstantValueGoverns
CONNECT_TIMEOUT15sTCP connect and key exchange
AUTH_RESPONSE_TIMEOUT60sHow long the daemon waits for a client to answer a credential prompt. Reached only when nothing answers and nothing cancels
SHUTDOWN_GRACE_PERIOD2sHow long a task may take to wind down after being asked to stop, before it is aborted. Reaching it logs a warning

The GUI side

The obsolete GUI is single-threaded, and its async work runs on the GLib main context via spawn_local. Shared client state sits in RefCell, which means a borrow must never be held across an await — if anything borrows the same cell while the future is suspended, the process panics with "already borrowed". The daemon client is Clone, so the pattern is to clone it out of the cell first: 

// Correct: the borrow ends before the await.
let client = state.daemon_client.borrow().clone();
if let Some(client) = client {
    match client.get_tunnel_status(id).await { /* ... */ }
}

Six sites violated this before v0.1.11. clippy::await_holding_refcell_ref catches it, and CI runs clippy with -D warnings.

The production GUI uses a different boundary: GTK objects remain on the GLib main context while an AppRuntime runs on a dedicated Tokio thread. Commands cross to the runtime and typed ControllerEvent/PresentationRequest messages return to GLib. The controller reduces each event into a new immutable snapshot before widgets render it. Blocking profile, key-file and Secret Service operations therefore do not run in widget callbacks, and Tokio never receives a GTK object.

Before that Tokio runtime exists, GUI v2 asks the toolkit-neutral ClientSetupRepository to classify local cli.toml state. Only a parsed and field-validated configuration can construct AppRuntime. Missing or invalid files remain in a non-blocking GTK setup flow, which can import cli-config.snippet or collect mode-specific settings. Saving uses a redacted draft and atomic 0600 replacement. This preflight does not contact or manage the daemon, and no daemon-originating text controls it.

4. Dependency strategy

Versions are pinned once in [workspace.dependencies] and inherited with { workspace = true }, so a bump happens in one place. Crate versions likewise inherit version.workspace = true. Both GUI crates use the same GTK 4.22, libadwaita 1.9, and glib/gio 0.22 binding generation.

Only what is used, and only from crates.io

Two rules, both enforced by cargo deny check on every pull request rather than by convention.

No git dependencies. A git dependency has no semver contract, so cargo update moves it to whatever the branch head happens to be rather than delivering a patch. It is also invisible to advisory scanners, which match crates.io name and version. The daemon spent nine months on a russh git snapshot carrying twelve advisories that cargo audit reported as clean, because it could not see it at all. A clean advisory report only means something if every dependency is one the scanner can read.

Features are listed explicitly. russh is built with default-features = false and only aws-lc-rs and rsa enabled. Dropping flate2 is what removes zlib from the negotiated compression list, eliminating the compression "zip bomb" class structurally rather than by patch; and the insecure des and dsa backends stay off regardless of what upstream later adds to its defaults.

Accepted risks — advisories with no available fix — are recorded in deny.toml with a written reason and a revisit condition, and listed in SECURITY.md. An ignore without a justification hides the next real finding.

Choosing a credential store at runtime

The keyring facade's compatibility API hard-codes Secret Service on Linux and ignores the keyutils feature entirely, so a v0.2.0 dependency upgrade moved every stored credential from the kernel keyring to Secret Service without anyone noticing. Using keyring-core and the store implementations directly makes the choice ours: it is selected at runtime, overridable with credential_store, and reported at startup rather than left implicit.

The secret-service feature must stay crypto-rust, not rt-tokio-crypto-rust. The tokio variant calls block_on internally, and the daemon's main is already #[tokio::main], so opening the store panics with "Cannot start a runtime from within a runtime" — a daemon that will not start. This is the feature set the keyring facade itself selects, which is why the store worked through it.

5. Testing strategy

Tests run in four tiers, split by what each needs in order to run at all. See DEVELOPMENT.md for how to run them.

TierWhatNeedsRuns
0Format, lint, supply-chain audit, secret scannothingevery pull request
1bCredential storage against a real Secret Servicegnome-keyring, dbus-run-sessionevery pull request
1Hermetic unit and integration testsnothingevery pull request
2Live SSH against an unprivileged localhost sshdsshd binary onlyevery pull request
3Live SSH against a provisioned remote hostreal accountsmanual

The split at tier 2 is what makes the SSH client path testable on every change. sshd runs perfectly well as an ordinary user on a high port with its own config and host key, so six of the ten live tests — including both host key verification tests — need no root, no container and no credentials. Password and 2FA go through PAM, which must read the shadow database and therefore needs privilege; those four are tier 3.

5.1 Test isolation

Every config path resolves through dirs::config_dir(), and the socket and PID file through dirs::runtime_dir(). On Linux those honour XDG_CONFIG_HOME and XDG_RUNTIME_DIR, so redirecting two variables gives a test run its own private tree — profiles, cli.toml, daemon.toml, daemon.token, known_hosts, the socket and the PID file. No production code needed changing to make this work.

scripts/sandbox.sh provides this for shell scripts. crates/daemon/tests/harness/ sets the same variables on the spawned daemon's environment rather than the test process's, so tests still run in parallel.

A test must never touch the developer's real ~/.config/ssh-tunnel-manager or a running daemon. Two tests used to: the pidfile test called PidFileGuard::create(), which resolves the real runtime path and would delete a live daemon's PID file, and the profile-manager tests read the real config directory. Use PidFileGuard::create_at() and the sandbox helpers instead.

5.2 Tier 1 — hermetic (cargo test)

No network, no secrets. Runs on every CI build.

  • Unit — config parsing and validation, profile TOML round-trip including the PasswordStorage boolean-to-enum migration, known_hosts entry parsing, token generation, TLS fingerprints, PID file recovery from stale and corrupt files
  • Integration (crates/daemon/tests/daemon_api.rs) — a real daemon process per test, driven through the REST/SSE API using the real client from common: health and info per listener mode, token missing/wrong/correct, the loopback-only rule for plain HTTP, socket 0600 and runtime dir 0700, token file 0600, the single-instance PID guard, and SSE connect, heartbeat and authentication

GUI-core tests cover reducer transitions, action availability, preference recovery and ordering, redacted editor behavior, FIFO authentication and the structured-text invariant. The production GUI adds tests for action routing, dialog selection, status mapping, ordering constraints and system-font/semantic-color CSS. Fedora 44 CI runs its locked test, Clippy, and release-build gates and explicitly compiles the obsolete GUI.

5.3 Tiers 2 and 3 — live SSH (cargo test -- --ignored)

Real connections to a real server, covering what nothing else can reach. Every test is #[ignore]d and skips when unconfigured, so it never runs by accident. make test-live-fixture stands up the tier-2 localhost sshd, runs the tier and tears it down; make test-live uses a provisioned host from scripts/provision-test-target.sh.

  • Host key verification on first connect, and refusal of a changed key
  • Key authentication, encrypted-key passphrase prompting, password authentication
  • A wrong password and a wrong 2FA code being re-prompted rather than failing the tunnel — the v0.1.10 fix, which nothing guarded until v0.1.11
  • 2FA with TOTP codes generated in-test, so no human is needed
  • Traffic actually flowing through the forward: the SSH banner is read back through the forwarded port
  • Teardown while connected, and teardown mid-authentication

Host names and credentials live only in .local/testing/ssh-target.env, which is gitignored in its entirety. No committed file — script, test, document or CI workflow — may contain them. The template is docs/testing/ssh-target.env.template.

An unconfigured live test skips but still reports ok, and the reason only goes to stderr — so a completely skipped run looks like a passing one. Locally, run the tier with --nocapture and read the SKIP lines. In CI that trap is closed rather than documented: SSH_TUNNEL_TEST_STRICT=1 makes a missing target file a failure, and =all additionally requires every account a test asks for.

5.4 Manual and script-level

  • scripts/dev-env.sh — a sandbox with a daemon, a wired cli.toml, seeded profiles per auth type and the debug binaries on PATH. This is how the GTK GUI is exercised; it is not automated.
  • scripts/test-network-modes.sh — drives the CLI against all three listener modes, including TLS certificate generation and fingerprint pinning.
  • Production GUI validation — functional Bazzite/live-daemon acceptance is complete. Keyboard-only and mockup screen comparison remain in .plan/UI_v2-final-validation.md.

5.5 CI

.github/workflows/ci.yml gates every push and pull request on cargo fmt --check, clippy with -D warnings, the hermetic tests, a release build, the network-mode script, the tier-2 live SSH fixture, cargo deny check and a gitleaks secret scan.

Because tier 2 needs no credentials, real SSH connections are exercised on untrusted pull requests safely. Tier 3 remains a separate workflow_dispatch job: it writes the target config from a secret and deletes it afterwards, and now fails when the secret is absent rather than reporting green having tested nothing.

Actions are pinned to commit SHAs rather than moving tags, and the toolchain is pinned by rust-toolchain.toml rather than floating on @stable. These workflows handle repository secrets, so an action that changes underneath them is a supply-chain hole.
