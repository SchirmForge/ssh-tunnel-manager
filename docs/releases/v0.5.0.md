# Release Notes - v0.5.0

**Release Date**: 2026-09-02

## Overview

Two things were broken in ways that looked like different problems and turned out to share a
cause: **clients stopped hearing from the daemon**, and **a daemon could be started that
nothing was able to reach**.

> ⚠️ **Breaking change: the daemon refuses to run as root.**
>
> A daemon started as root now exits at startup with an explanation. If you were running it as
> root to forward ports below 1024, grant the capability instead:
>
> ```bash
> sudo setcap cap_net_bind_service=+ep /path/to/ssh-tunnel-daemon
> ```
>
> then start the daemon as your normal user. Under systemd, the shipped unit already sets
> `AmbientCapabilities=CAP_NET_BIND_SERVICE` — no change needed. See
> [architecture/SYSTEMD.md](../architecture/SYSTEMD.md).

## Key Highlights

### 🔌 Authentication prompts survive a reconnect

Starting a password-authenticated tunnel could fail with `Authentication prompt timed out after
60s` **even with a client attached and waiting**. Three faults compounded:

| | |
|---|---|
| The stream was cut every 30 seconds | It was built with a *total* request timeout. In `reqwest` that covers the response body, so a streaming request dies on schedule no matter how much traffic is flowing. |
| The backoff never recovered | It doubled on every attempt with no reset after a connection that worked, so the client settled into a permanent 30s-connected / 30s-disconnected cycle. |
| A prompt raised in the gap was gone for good | The daemon broadcast only to subscribers live at that instant. Nothing replayed it. |

Each alone is survivable. Together they meant roughly half of all events were broadcast to
nobody, and an authentication prompt that landed in a dead window was never seen again.

Now: the stream uses a **read** timeout, so it dies only when nothing arrives; the backoff
**resets** after a connection that lasted; and the daemon **re-sends outstanding prompts to
every new subscriber**.

### 🆔 Re-delivery keeps the same request id

Re-sending a prompt raises an obvious question: new id, or the same one? The same one — because
**the id identifies the question, not the delivery**.

Issuing a fresh id per delivery looks like it sidesteps duplicate handling, but it breaks the
case that matters more. A second client connecting would cause the daemon to reissue the id,
which stales the id the *first* client is holding, and its answer then fails with "Request ID
mismatch". Correctness would depend on how many clients happened to be attached.

So delivery is at-least-once with a stable identity, and clients dedupe. A genuinely new
question — the prompt after a rejected password — still gets a genuinely new id.

Only `Password` and `KeyPassphrase` are ever answered from storage. A TOTP code is valid for one
time step, keyboard-interactive text is server-supplied and must be shown verbatim, and a host
key is a trust decision. A *changed* host key is not a prompt at all: it aborts the connection,
and this release does not touch that path.

### 🧭 One event path for the CLI and the GUI

The reason the stream bug survived so long is that there were two client architectures. The GUI
used a long-lived `EventListener`; the CLI's `start_tunnel_with_events` carried **its own
hand-rolled SSE subscription and parsing**, built on the request client — so fixing the timeout
on one path left the other broken. The CLI is now built on the same `EventListener`.

`gui-core::events` has been removed outright: its `TunnelEventHandler` had zero implementors
anywhere and implied a sharing between front-ends that did not exist.

### 🚫 The daemon will not run as root

Running as root never worked, and could not be made to work by adjusting permissions. The
socket goes in `$XDG_RUNTIME_DIR`, which for root in a login shell is `/run/user/0` — a
per-user directory that is **mode 0700 by design**. No other user can traverse it, so the CLI
and the GUI simply reported that no daemon was running. Widening the socket would not have
helped either: the daemon only ever chmods, so it stayed owned by `root:root`.

Root bought exactly one thing — binding forward ports below 1024 — and `CAP_NET_BIND_SERVICE`
grants that without handing the daemon, and every SSH key it opens, the rest of root's
authority.

The privileged-port error message used to say *"Run the daemon with: sudo ssh-tunnel-daemon"*.
That advice is gone; it is the most likely reason anyone tried it.

### 📁 The socket is where clients look for it

Two related path defects, both affecting a daemon with no desktop session:

- **A service account could not start the daemon at all** in Unix-socket mode. Path resolution
  failed outright when `$XDG_RUNTIME_DIR` was unset, which is exactly the case for a dedicated
  account with no login session. It now falls back to `/run/ssh-tunnel-manager` — the location
  clients were *already* looking in, and the one the systemd unit creates.
- **The PID file and the socket could end up in different directories.** They were derived
  independently, and disagreed whenever `$XDG_RUNTIME_DIR` was already the daemon's own
  directory — which is precisely what the shipped systemd unit sets. The PID file landed in a
  nested `ssh-tunnel-manager/ssh-tunnel-manager/`, outside the `RuntimeDirectory=` systemd
  creates and cleans up. Both now come from one place.

## Also fixed

- **A repeated prompt erased itself in the GUI.** `add_pending_auth` inserted by request id and
  then removed the previous id for that tunnel — which, on a repeat, is the entry it had just
  inserted.
- **The CLI would prompt and submit twice** for a re-delivered request, the second submit
  failing and surfacing as a spurious error.
- **One credential policy.** Whether a prompt may be answered from client-side storage is now
  decided in one place rather than by two mechanisms that happened to agree.
- Ports are reported as privileged when below 1024 rather than at or below it.

## Testing

Two of this release's fixes are in the test tooling itself, and both are the kind of fault that
makes a suite worse than useless because it reports success:

- **`make test-live` passed while running nothing.** With no target configured it skipped every
  test and still reported `ok`. It now runs strict and fails loudly.
- **The tier-2 fixture destroyed provisioned credentials.** It shares one private target
  configuration with the provisioned tiers and overwrote it on `up`, so running the local
  fixture silently wiped a real target's configuration — after which the
  provisioned tier skipped everything and still reported `ok`. It now preserves and restores it.
- The tier-2 live suite runs in **5.3 seconds instead of 300**. A never-answering test handler
  used a blocking `thread::sleep(300)`, which parks a runtime worker that `JoinHandle::abort()`
  cannot interrupt, so the runtime's drop waited it out.

The new reconciliation test was checked against the *unfixed* daemon to confirm it fails there.
An earlier version of the stream-longevity test passed against broken code — it counted
heartbeats within a window that fit inside the 30-second cliff — and was rewritten.

## Known Issues

- **Manual GUI validation is outstanding.** The reconnection behaviour is covered by unit tests
  and by live tests against a real SSH server, but three checks need a human at a desktop: the
  hand reproduction of the original report, confirming an idle GUI holds one long-lived
  `GET /api/events` rather than one every 30 seconds, and running the CLI and GUI together. The
  previous release marked the stream-recovery story as done while it was in fact broken, so
  this is called out rather than assumed.
- **The root refusal has no override**, so a container image that runs the daemon as root will
  now fail to start. Nothing in this repository ships such an image.
- `ssh-tunnel daemon status` is still unimplemented.
- **Token in `cli-config.snippet`** — the file is `0600` but holds the token in plaintext.
- **Auto-reconnect is still not implemented.**

See [KNOWN_ISSUES.md](../KNOWN_ISSUES.md) for the full list.

## For Contributors

1. **Use `create_streaming_client` for anything that reads a stream.** The request client's
   total timeout cuts a stream at 30 seconds regardless of traffic. The read timeout is set
   against the 10-second heartbeat — two missed beats — and the dependency is commented at both
   ends, because a later heartbeat change would otherwise silently reintroduce this.
2. **`EventListener::listen_ready()`** does not return until the stream is established. A caller
   about to *cause* events must be subscribed before it acts.
3. **A blocking call in a test handler parks a runtime worker**, and `JoinHandle::abort()`
   cannot interrupt it. Use the releasable `ParksUntilReleased` helper and a multi-threaded
   runtime.

## Upgrading

```bash
# From packages
sudo dpkg -i ssh-tunnel-daemon_0.5.0-0_amd64.deb \
             ssh-tunnel-cli_0.5.0-0_amd64.deb \
             ssh-tunnel-gui-gtk_0.5.0-0_amd64.deb
systemctl --user restart ssh-tunnel-daemon

# From source (needs Rust 1.85)
git pull && cargo build --release
```

**If you were running the daemon as root**, it will now refuse to start. Grant
`CAP_NET_BIND_SERVICE` as shown at the top of these notes and run it as a normal user. Any
leftover root-owned files in `/run/user/0/ssh-tunnel-manager/` can be deleted.
