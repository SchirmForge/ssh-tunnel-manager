# Release Notes - v0.3.0

**Release Date**: 2026-09-01

## Overview

Version 0.3.0 is about **credential storage**, and the headline is a defect that has been
present since remote daemon support arrived:

> **"Store in keychain" never worked when the daemon ran on another machine.**

The credential was written to the client's keychain and looked for on the daemon's. With the
daemon on your LAN those are different machines, so nothing was found and you were prompted
anyway — silently, with no error, every time. If you have been ticking "remember this
password" and still being asked for it, that is why.

The cause was a setting that recorded only *that* a credential existed, never *where*.
`password_storage = "keychain"` said "a keychain" without saying whose. That is now explicit,
and a credential kept on the client is answered by the client — which works identically
whether the daemon is local or across the network.

**Upgrade notes**: no action needed. Credentials saved by an earlier version are found and
migrated automatically; profiles are updated as they are used.

> ⚠️ **Downgrading to v0.2.0 is not clean.** A profile saved by v0.3.0 records
> `password_storage = "client"`, which v0.2.0 rejects with *"unknown password storage type"*.
> If you need to roll back, edit those profiles to `"keychain"` or recreate them.

## Key Highlights

### 🔑 Saved credentials work with a remote daemon

`password_storage` now records **where** a credential is:

| Value | Kept | Read by |
|---|---|---|
| `client` | on the client | the client, which answers when the daemon asks |
| `daemon-host` | on the daemon host | the daemon, directly |
| `none` | nowhere — prompted each time | — |
| `keychain` | *legacy*, resolved on use | see below |

`client` is the one that fixes the LAN case, and it needed **no daemon change at all**: the
daemon raises its usual prompt over SSE and waits, and a stored answer arrives instead of a
typed one, over the same authenticated channel. The daemon is not even told the client holds
a credential — that would only invite it to look for one.

The legacy `keychain` value is still read, because profiles are TOML that people copy and
back up. It resolves to `daemon-host` for a local daemon and `client` for a remote one, which
is what was meant in each case. It is no longer written.

### 🗄️ The credential store is chosen, not assumed

The daemon now picks a store at runtime and **says which one it picked**:

```
INFO Credential store: Secret Service
```

`auto` (default) prefers Secret Service and falls back to the Linux kernel keyutils keyring,
so a desktop and a headless server both work with no configuration. Force it with
`credential_store` in `daemon.toml`:

```toml
credential_store = "auto"   # or "secret-service", "keyutils", "none"
```

On a headless host the daemon warns that credentials in the kernel keyring do not survive a
reboot.

Reporting this is a security property rather than a nicety. A change of backing store is
otherwise indistinguishable from an empty keyring — which is exactly what happened in v0.2.0.

### 🔄 Credentials saved before v0.2.0 are recovered

The v0.2.0 dependency upgrade moved the backing store from the kernel keyring to Secret
Service, so anything saved earlier became invisible. Those credentials are now found, adopted
into the current store, and the original removed.

Moved rather than copied, deliberately: two copies of one secret drift apart, and a later
reader could get the stale one. One-directional too — never Secret Service to the kernel
keyring, which would take a credential that survives a reboot and put it somewhere that does
not.

### 🧪 Credential storage is tested

The module had **no tests at all** before this release, which is how both the v0.2.0 store
change and the remote-daemon defect reached users. It now has 13 unit tests over an injectable
fake, and 8 against a real Secret Service in a throwaway D-Bus session:

```bash
make test-keychain-live
```

One of those is worth explaining. A write followed by a read passes even when the backing
store changes, because both go to the new store. What actually breaks is persistence *across
processes* — the GUI writes, and the daemon reads later from a different process. So the test
re-execs itself and asserts the credential comes back. That is the check that would have
caught v0.2.0.

### 🐛 Also fixed

**`has_password` distinguishes "nothing stored" from "cannot reach the store."** Collapsing
those is what made a changed backing store look like an empty keyring rather than an
unreachable one.

**A stored credential is offered once per attempt.** The server re-prompts on a rejection, and
replaying a stale credential would exhaust its `MaxAuthTries` without you ever being asked —
the same trap fixed on the daemon side in v0.2.0, and easy to reintroduce on the client.

## Known Issues

- **The GTK GUI still records the legacy storage value** when saving a credential. It works
  against a local daemon, as it always has, and is read correctly everywhere. Profiles created
  with the CLI get the corrected value. This is being handled with the GUI rework rather than
  by patching the outgoing front-end.
- **Credentials in the kernel keyring do not survive a reboot.** That is the trade-off for
  needing no desktop session. Genuinely unattended operation — a daemon reconnecting on its
  own after a restart — needs work that is planned but not in this release.
- `ssh-tunnel daemon status` is still unimplemented, so the credential store is visible in the
  daemon log and the API but not from the CLI.
- **Token in `cli-config.snippet`** — the file is `0600` but holds the token in plaintext.
  Delete it after copying.
- **Auto-reconnect is still not implemented.**

See [KNOWN_ISSUES.md](../KNOWN_ISSUES.md) for the full list.

## For Contributors

1. **`make test-keychain-live`** runs credential-storage tests against a real Secret Service.
   Needs `gnome-keyring` and `dbus-run-session`; both are in `containers/Containerfile.dev`,
   so rebuild your dev container if it predates this release.
2. **Do not change the secret-service crate feature to `rt-tokio-crypto-rust`.** That variant
   calls `block_on` internally and the daemon's `main` is already `#[tokio::main]`, so opening
   the store panics with *"Cannot start a runtime from within a runtime"* — a daemon that will
   not start. There is a comment saying so at the declaration.
3. **`PasswordStorage` is `Copy`**, and `resolved()` turns the legacy value into a definite
   one once the daemon's location is known. Use `is_client_held()` / `is_daemon_held()` rather
   than matching on variants.

See [DEVELOPMENT.md](../DEVELOPMENT.md#testing) and
[architecture/SECURITY.md](../architecture/SECURITY.md) for the credential model.

## Upgrading

```bash
# From packages
sudo dpkg -i ssh-tunnel-daemon_0.3.0-0_amd64.deb \
             ssh-tunnel-cli_0.3.0-0_amd64.deb \
             ssh-tunnel-gui-gtk_0.3.0-0_amd64.deb
systemctl --user restart ssh-tunnel-daemon

# From source (needs Rust 1.85)
git pull && cargo build --release
```
